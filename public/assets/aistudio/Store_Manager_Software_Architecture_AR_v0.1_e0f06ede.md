# وثيقة التصميم المعماري الشاملة
## نظام إدارة المتاجر والمخزون والمبيعات

**الإصدار:** 0.1  
**اللغة:** العربية  
**الغرض:** وثيقة مرجعية للتدقيق المعماري والتخطيط والتنفيذ.

> هذه الوثيقة هي مرجع متطلبات وقرارات المشروع. لا تبدأ كتابة الكود قبل تدقيقها، وتثبيت القرارات المفتوحة، والحصول على موافقة صريحة.

وثيقة التصميم المعماري الشاملة

نظام إدارة المتاجر والمخزون والمبيعات

Windows + Android | Local-First | Offline-Capable | LAN

الإصدار 0.1 — وثيقة تأسيسية للمراجعة قبل بدء التنفيذ.

الهدف: برنامج تجاري يُباع بترخيص، ويعمل محلياً دون اشتراك سحابي إلزامي، مع دعم Windows وAndroid وعدة أجهزة داخل متجر واحد.

1. الملخص التنفيذي

النظام المقترح برنامج مرن لإدارة المتاجر الصغيرة والمتوسطة: المنتجات والتصنيفات والمخزون والمبيعات والمشتريات والعملاء والموردون والديون والمدفوعات والمصروفات والتقارير والفواتير. يدعم المتاجر المختلطة، ولا يفرض خصائص لا تنطبق على المنتج.

1.1 القرارات المعتمدة

- دعم Windows وAndroid منذ الإصدار الأول، بنواة أعمال مشتركة.
- متجر/موقع تجاري واحد في الترخيص الأساسي؛ لا توجد إدارة فروع متعددة في النطاق الحالي.
- عدة مستخدمين بصلاحيات مختلفة، وعدة أجهزة متصلة عبر شبكة LAN.
- اختيار نشاط رئيسي وأنشطة إضافية اختياري لتقديم قوالب واقتراحات فقط.
- اسم المنتج هو الحقل الإلزامي عند إنشاء المنتج؛ بقية الحقول اختيارية.
- العمل دون إنترنت، مع نسخ احتياطي واستعادة محليين.
- البرنامج يقترح والعميل يقرر؛ الخصائص مثل اللون والمقاس والصلاحية غير إلزامية.
1.2 خارج النطاق الحالي

- إدارة عدة فروع مستقلة ضمن ترخيص واحد.
- خدمة سحابية إلزامية أو اشتراك لتشغيل الوظائف الأساسية.
- محاسبة قانونية متكاملة أو إقرارات ضريبية قبل التحقق من المتطلبات المحلية.
- متجر إلكتروني وبوابة دفع إلكتروني ومزامنة بين مواقع جغرافية مختلفة.
2. الرؤية والمستخدمون

- مالك المتجر ومديره: الإعدادات، التقارير، الصلاحيات والنسخ الاحتياطي.
- البائع: البحث عن المنتجات وتسجيل المبيعات والمدفوعات وطباعة الإيصالات.
- مسؤول المخزون: الاستلام والجرد والتسويات والمرتجعات.
- الموظف على Android: البيع أو البحث أو متابعة المخزون حسب الصلاحيات.
قائمة الأنشطة المقترحة تشمل المواد الغذائية، الملابس والأحذية، الهواتف والإلكترونيات، قطع الغيار، مستحضرات التجميل والعطور، الأثاث والمنزل، مواد البناء والسباكة، المكتبات، الزراعة والأعلاف، المطاعم، الهدايا والألعاب، ونشاطاً آخر. النشاط لا يمنع إضافة أي منتج أو تصنيف.

3. المتطلبات الوظيفية

3.1 إعداد المتجر

- اسم المتجر وبياناته وشعاره وبيانات الفاتورة.
- النشاط الرئيسي والأنشطة الإضافية اختيارية.
- العربية والفرنسية، مع RTL/LTR صحيح.
- الدينار الجزائري DZD افتراضياً مع قابلية تغيير العملة.
- إعدادات التاريخ والضرائب والرسوم والطباعة قابلة للتعديل.
3.2 المنتجات والتصنيفات

- الاسم إلزامي؛ التصنيف والوصف والصورة والرمز الداخلي اختيارية.
- سعر البيع وتكلفة الشراء والكمية والحد الأدنى والباركود والمورد الافتراضي اختيارية.
- خصائص حرة مثل المقاس واللون والحجم والقطر والعمر المناسب وتاريخ الصلاحية.
- متغيرات المنتج لها SKU وباركود ورصيد مستقل عند الحاجة.
- وحدات قياس متعددة: قطعة، صندوق، كرتون، كغ، لتر، متر وغيرها، مع تحويلات.
- باركود واحد أو أكثر للمنتج أو المتغير.
- استيراد CSV/XLSX مع معاينة الأخطاء قبل الحفظ، وتصدير البيانات.
قاعدة مهمة: يجب التمييز بين منتج لا يتتبع المخزون وبين منتج يتتبع المخزون ورصيده صفر. غياب الكمية لا يعني تلقائياً أن الكمية صفر.

3.3 المخزون

- دفتر حركات: استلام، بيع، مرتجع، تلف، فقد، تسوية وجرد.
- رصيد حالي ناتج عن الحركات، مع سجل تاريخي وسبب لكل تسوية.
- تنبيه انخفاض المخزون، وجرد فعلي ومقارنة الفروقات.
- دفعات وتواريخ صلاحية وأرقام تسلسلية كميزات اختيارية.
- منع المخزون السالب افتراضياً، مع إمكانية تفعيله بصلاحية مدير.
3.4 المبيعات ونقطة البيع POS

- بحث بالاسم والرمز والباركود، وسلة سريعة تدعم تعدد المنتجات.
- تعديل الكمية والخصم وسعر البيع وفق الصلاحيات.
- إذا لم يكن للمنتج سعر افتراضي، يمكن إدخال السعر عند البيع وفق صلاحية المستخدم.
- دفع نقدي أو جزئي أو آجل، وطرق دفع قابلة للتسمية.
- فواتير مرقمة، مسودات، إرجاع وإلغاء موثق بإجراء عكسي.
- وردية صندوق ومطابقة النقد ميزة احترافية.
3.5 المشتريات والأطراف التجارية

- الموردون والعملاء وبيانات الاتصال وكشوف الحساب.
- مستند شراء بمراحل: مسودة، مستلم جزئياً، مستلم بالكامل، ملغى.
- زيادة المخزون عند اعتماد الاستلام فقط.
- دفعات جزئية للموردين والعملاء وربط كل دفعة بالذمة أو الفاتورة.
- مرتجعات الموردين والعملاء مع عكس الأثر على المخزون والحسابات.
3.6 المصروفات والتقارير

- مصروفات بفئات قابلة للتخصيص.
- تقارير المبيعات اليومية والشهرية، حسب المنتج والتصنيف والموظف وطريقة الدفع.
- الأكثر والأقل مبيعاً، المنتجات الراكدة، قيمة المخزون، والنواقص.
- إجمالي المبيعات، تكلفة البضاعة المباعة، هامش الربح، المصروفات وصافي الربح التقديري.
- تصدير PDF وCSV/XLSX.
لا يُعرض الربح على أنه محاسبة قانونية أو نتيجة ضريبية رسمية. عند غياب تكلفة الشراء يجب إظهار أن هامش الربح غير مكتمل.

3.7 الموظفون والصلاحيات

- أدوار: مدير، بائع، مسؤول مخزون، تقارير/محاسب، مع تخصيص الصلاحيات.
- التحكم في تعديل الأسعار والخصومات والبيع الآجل والمرتجعات والتقارير والأرباح.
- سجل تدقيق يحدد من نفذ العملية ومتى وعلى أي جهاز.
- كلمات المرور لا تخزن كنص صريح؛ تستخدم خوارزمية اشتقاق آمنة.
4. المتطلبات غير الوظيفية

| المجال | المطلب |
| --- | --- |
| الأداء | بحث سريع، تحميل تدريجي، وعدم تحميل كل البيانات دفعة واحدة. |
| التوفر | الوظائف الأساسية تعمل دون إنترنت؛ LAN يتطلب توفر المضيف. |
| سلامة البيانات | معاملات ذرية، مفاتيح فريدة، ومنع تكرار العمليات. |
| الأمان | مصادقة وصلاحيات وتشفير نسخ احتياطية وحماية واجهة الشبكة. |
| الخصوصية | بيانات المتجر محلية ولا ترسل للخارج دون موافقة. |
| قابلية الصيانة | فصل واجهة المستخدم عن قواعد الأعمال والتخزين والنقل. |
| النسخ الاحتياطي | نسخ مجدول ويدوي، والتحقق من سلامة النسخة واختبار الاستعادة. |
| التدويل | العربية RTL والفرنسية LTR، مع اختبار الأرقام والرموز المختلطة. |

5. المعمارية التقنية المقترحة

الترشيح المبدئي هو Kotlin + Compose Multiplatform لتطبيق Windows وAndroid، مع Ktor لخدمة الشبكة المحلية وSQLite للتخزين. هذه اختيارات مرشحة وليست نهائية حتى ينجح نموذج إثبات التقنية.

| الطبقة | التقنية المبدئية | الغرض |
| --- | --- | --- |
| اللغة | Kotlin | منطق مشترك بين المنصتين. |
| واجهة المستخدم | Compose Multiplatform | واجهات متكيفة لـ Windows وAndroid. |
| قاعدة البيانات | SQLite عبر SQLDelight أو مكتبة KMP مثبتة | تخزين محلي وترحيلات. |
| خدمة LAN | Ktor Server | API محلية على مضيف Windows. |
| عميل الشبكة | Ktor Client | اتصال تطبيقات Windows/Android بالمضيف. |
| التسلسل | kotlinx.serialization | عقود طلبات واستجابات. |
| الاختبارات | kotlin.test واختبارات تكامل | اختبار قواعد الأعمال والمنصات. |

5.1 الطبقات

- Presentation: الشاشات والتنقل وحالة الواجهة.
- Application: حالات الاستخدام مثل CreateProduct وCompleteSale وReceivePurchase.
- Domain: الكيانات وقواعد العمل والحسابات دون اعتماد على UI أو قاعدة البيانات.
- Data: المستودعات وDAO والترحيلات والتخزين المحلي.
- Network: API والمصادقة وإعادة المحاولة ومنع التكرار.
- Platform: الطباعة والكاميرا والباركود والملفات والإشعارات وخدمة Windows.
5.2 وضع الجهاز الواحد ووضع الشبكة

في وضع الجهاز الواحد يعمل التطبيق مع قاعدة محلية. في وضع LAN يكون جهاز Windows المضيف هو المرجع المركزي: يشغل خدمة محلية وقاعدة البيانات. واجهة Windows على المضيف تتصل بالخدمة عبر loopback، وتتصل الأجهزة الأخرى عبر شبكة المحل.

لا نشارك ملف SQLite مباشرة عبر SMB أو مجلد شبكي بين الأجهزة؛ كل الوصول يمر عبر API على المضيف لضمان المعاملات والصلاحيات والتزامن.

| الوضع | السلوك |
| --- | --- |
| Windows منفرد | واجهة + خدمة محلية + قاعدة محلية. |
| Android منفرد | قاعدة محلية داخل التطبيق؛ لا توجد مشاركة تلقائية. |
| متعدد الأجهزة | Windows Host + API LAN + قاعدة مركزية + عملاء Windows/Android. |
| النسخ والاستعادة | نسخة احتياطية منظمة ومشفرة، واستعادة بصلاحية المدير. |

يُفضّل Windows كمضيف في الإصدار الأول؛ لأن تشغيل خدمة مستمرة والطباعة والنسخ الاحتياطي أسهل إدارياً من Android. يمكن دراسة مضيف Android مستقبلاً.

6. تصميم قاعدة البيانات

6.1 قواعد عامة

- معرفات UUID/ULID ثابتة.
- الأموال تخزن كأعداد صحيحة بوحدة العملة الصغرى أو Decimal مضبوط، لا Float/Double.
- سطر الفاتورة يحتفظ بنسخة من اسم المنتج وسعره وقت البيع.
- لا تحذف الحركات المالية أو المخزنية المعتمدة؛ تُعكس بسجلات عكسية.
- ترحيلات قاعدة البيانات مرقمة ومختبرة.
| الكيان | المحتوى |
| --- | --- |
| StoreProfile | بيانات المتجر والعملة واللغة والإعدادات. |
| User, Role, Permission | المستخدمون والأدوار والصلاحيات. |
| Device | الأجهزة المسجلة وآخر اتصال وحالة الترخيص. |
| Category | التصنيفات. |
| Product | الاسم والوصف والتصنيف وحالة تتبع المخزون. |
| ProductVariant | المقاس/اللون/الحجم وSKU والباركود. |
| AttributeDefinition/Value | خصائص المنتج المرنة. |
| UnitOfMeasure/Conversion | وحدات القياس والتحويل. |
| Customer/Supplier | العملاء والموردون. |
| Sale/SaleLine | الفواتير وسطور البيع والأسعار التاريخية. |
| Purchase/PurchaseLine | المشتريات والاستلام. |
| Payment/PaymentAllocation | الدفعات وتوزيعها على الذمم. |
| InventoryMovement/Balance | دفتر حركات المخزون والأرصدة. |
| Batch/SerialNumber | دفعات الصلاحية والأرقام التسلسلية. |
| Expense/CashSession | المصروفات وورديات الصندوق. |
| AuditLog/BackupRecord | التدقيق والنسخ الاحتياطي. |

6.2 خصائص المنتجات المرنة

نستخدم نموذجاً هجيناً: الحقول الشائعة في أعمدة صريحة، والخصائص القابلة للتخصيص في جداول AttributeDefinition وProductAttributeValue. لا نعتمد على JSON حر لكل بيانات المنتج، لأن ذلك يضعف البحث والفهرسة والتقارير.

6.3 المخزون والمال

كل بيع معتمد ينشئ حركة خروج، وكل استلام شراء ينشئ حركة دخول، والمرتجع والتالف والتسوية حركات مستقلة. يجب تحديث الفاتورة والدفع وحركة المخزون في معاملة متسقة قدر الإمكان.

مثال: فاتورة 10,000 دج، دفع العميل 6,000 دج، فيبقى 4,000 دج ديناً. تسديد الـ4,000 لاحقاً يغلق الذمة ولا يسجل مبيعات جديدة.

7. الشبكة والتزامن والعمل دون اتصال

7.1 الاتصال

- إدخال عنوان IP أو اسم المضيف أو الاقتران برمز؛ لا نعتمد على الاكتشاف الآلي وحده.
- API بإصدارات مثل /api/v1، مع مصادقة ورموز وصول.
- الخدمة محصورة افتراضياً في LAN ولا تفتح على الإنترنت.
- إمكانية إلغاء تسجيل جهاز مفقود.
7.2 الانقطاع

عند انقطاع عميل عن المضيف لا يمكن ضمان مخزون موحد إذا اعتمدت أجهزة متعددة مبيعات مستقلة. لذلك في الإصدار الأول:

| العملية أثناء الانقطاع | السياسة |
| --- | --- |
| تصفح بيانات مخزنة | مسموح مع بيان أن البيانات قديمة. |
| إنشاء مسودة بيع | مسموح محلياً. |
| اعتماد بيع يؤثر في مخزون مشترك | يتوقف حتى عودة الاتصال. |
| تسجيل تحصيل طارئ | يمكن حفظه كعملية معلقة غير معتمدة مركزياً، مع مراجعة لاحقة. |
| تعديل الأسعار والمنتجات | يُفضّل اشتراط الاتصال بالمضيف. |

كل طلب يحمل operationId فريداً لمنع تكرار البيع أو الدفع عند إعادة الإرسال. ويعيد الخادم التحقق من الرصيد والسعر والصلاحية لحظة اعتماد العملية.

7.3 التزامن

تُستخدم معاملات وقفل/تحديث ذري عند اعتماد البيع. إذا حاول موظفان بيع آخر قطعة في اللحظة نفسها، يجب ألا تُعتمد العمليتان معاً إذا كان منع المخزون السالب مفعلاً.

8. الأمان والخصوصية

- تشفير النسخ الاحتياطية وحماية مفاتيحها.
- عدم تخزين كلمات المرور كنص صريح.
- عدم تخزين بيانات البطاقات البنكية الحساسة.
- سجل تدقيق للخصومات الكبيرة وتعديل الأسعار والمرتجعات والتسويات.
- قفل تلقائي للجلسة وإخفاء بيانات التكلفة والأرباح عن غير المخولين.
- تحديثات موقعة رقمياً، وعدم إرسال بيانات المتجر إلى المطور دون موافقة.
9. النسخ الاحتياطي والاستعادة

- نسخ تلقائي مجدول ونسخ يدوي قبل التحديثات.
- نسخ متعددة على قرص خارجي أو مجلد يختاره العميل.
- التحقق من سلامة النسخة قبل إعلان نجاحها.
- اختبار الاستعادة إلى قاعدة مؤقتة قبل استبدال القاعدة الحالية.
- تضمين الصور والمرفقات أو ملف manifest يربطها بالنسخة.
- التنبيه إلى أن النسخ على القرص نفسه لا تحمي من تلفه أو سرقته.
10. الطباعة والأجهزة

- فواتير A4 وإيصالات حرارية 58mm و80mm، مع اختبار العربية فعلياً.
- معاينة قبل الطباعة وتخصيص الشعار والهوامش وعدد النسخ.
- قارئ USB كلوحة مفاتيح على Windows، وكاميرا أو قارئ Bluetooth/HID على Android.
- إدخال يدوي بديل عند فشل المسح.
- الميزان ودرج النقود وطابعة الملصقات إضافات مستقبلية بعد اختبار الأجهزة.
11. واجهات المستخدم

11.1 Windows

- قائمة جانبية ولوحة تحكم.
- POS مناسب للفأرة ولوحة المفاتيح والباركود.
- جداول ببحث وفرز وفلاتر.
- إعداد المضيف وحالة الشبكة والنسخ الاحتياطي.
11.2 Android

- تصميم متجاوب للهاتف واللوحي.
- أزرار لمس كبيرة وشاشة بيع مبسطة.
- مسح الباركود بالكاميرا.
- عرض واضح لحالة الاتصال بالمضيف.
- إخفاء وظائف الإدارة حسب الصلاحيات.
11.3 العربية والفرنسية

واجهة العربية RTL والفرنسية LTR. يجب اختبار الأرقام والباركود والهواتف والأسعار المختلطة، وعدم عكس الرموز أو ترتيب النصوص.

14. الترخيص والتوزيع

- ترخيص لمتجر/موقع واحد؛ إدارة الفروع المتعددة خارج النطاق الحالي.
- عدد الأجهزة ضمن الباقة يحدد بوضوح مع السماح بتشغيل أجهزة المتجر المتفق عليها.
- الترخيص محلي وموقع رقمياً؛ لا يُخزن سر توقيع المطور داخل التطبيق.
- فترة سماح وآلية نقل ترخيص عند تعطل الحاسوب.
- عدم قفل بيانات العميل أو تعطيل الوصول إليها بسبب تعذر التحقق من الترخيص.
- التحديثات والدعم يمكن أن يكونا اختياريين، مع توضيح حقوق النسخة المشتراة.
15. الاختبارات وضمان الجودة

- إضافة منتج باسمه فقط دون سعر أو كمية أو باركود.
- إنشاء متجر مختلط يبيع العطور والأحذية والحفاظات والسباكة والتنظيف والألعاب.
- منتج بمتغيرات ومخزون مستقل لكل متغير.
- بيع بسعر يدوي عندما لا يوجد سعر افتراضي.
- دفع جزئي ثم تسديد الرصيد دون تكرار الإيراد.
- شراء مستلم جزئياً، مرتجع، تسوية وجرد.
- محاولة موظف غير مخول تعديل سعر أو الاطلاع على الأرباح.
- جهازان يحاولان بيع آخر قطعة في اللحظة نفسها.
- انقطاع LAN وإعادة إرسال طلب بيع دون تكراره.
- إعادة تشغيل المضيف أثناء اتصال العملاء.
- استعادة نسخة احتياطية والتحقق من الأرصدة والصور والفواتير.
- اختبار طباعة فعلية بالعربية على A4 وحراري.

17.1 قرارات يجب حسمها قبل التنفيذ

- أدنى إصدار Windows وAndroid مدعوم.
- هل يمكن لأي Windows أن يكون المضيف أم نحدد حاسوباً رئيسياً؟
- عدد الأجهزة المسموح بها في كل ترخيص.
- سياسة المخزون السالب.
- طريقة تكلفة المخزون: المتوسط المرجح أم FIFO.
- هل ندعم عدة صناديق/ورديات في MVP؟
- متطلبات الفاتورة والضرائب بعد التحقق القانوني.
18. معايير قبول MVP

- متجر مختلط لا تقيده قائمة النشاط.
- إضافة منتج بالاسم فقط.
- خصائص ومتغيرات اختيارية قابلة للتوسع.
- مبيعات ومشتريات ومرتجعات وتسويات مع سجل واضح.
- ديون ودفعات جزئية وكشوف حساب.
- تطبيق Windows وتطبيق Android يعملان.
- وضع جهاز واحد دون إنترنت.
- وضع LAN بقاعدة مركزية على Windows.
- منع تكرار العمليات عند إعادة الإرسال.
- صلاحيات وسجل تدقيق.
- طباعة عربية على طابعة A4 وحرارية تم اختبارهما.
- نسخ احتياطي واستعادة ناجحان.
19. الخلاصة

التوصية هي بناء نواة Kotlin مشتركة مع واجهتي Windows وAndroid، وقاعدة محلية في وضع الجهاز الواحد، وخدمة Windows محلية مع قاعدة مركزية في وضع LAN. لا تتم مشاركة ملف SQLite مباشرة عبر الشبكة. وفي الإصدار الأول لا تُعتمد مبيعات مخزنية مشتركة عند فقد الاتصال بالمضيف؛ يمكن حفظ مسودات فقط.

الخطوة التالية ليست بناء جميع الشاشات؛ بل تنفيذ نموذج إثبات التقنية للتحقق من بناء المنصتين، قاعدة البيانات، خدمة LAN، والعربية والطباعة. بعد نجاحه تثبت التقنية ثم يبدأ التطوير المرحلي.
